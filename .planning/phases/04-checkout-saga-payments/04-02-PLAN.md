<objective>
Extend the existing `OrderStateMachine` (built in Phase 3, ADR-0005) to orchestrate the full checkout saga: publish `AuthorisePayment` on order creation, react to `PaymentAuthorised`/`PaymentFailed` (CHK-03), react to `FulfillmentFailed` with a refund-and-cancel compensation (CHK-04), and enforce a configurable saga timeout via MassTransit `Schedule`/`Unschedule` (CHK-05). This is backend saga logic only — no HTTP endpoints yet (plan 04-03) and no real Payments consumer yet (plan 04-04); correctness is proven via the existing in-memory saga unit-test harness.

Before the ASB-native `Schedule`/`Unschedule` mechanism is trusted for CHK-05, this plan first runs a standalone, automated spike (Task 2) against the real ASB emulator image to confirm it actually honors `ScheduledEnqueueTime` — RESEARCH.md flags this as "the single largest technical risk" and prescribes exactly this verification before committing to the approach. The spike is fully automated (Docker plus a throwaway console app), decoupled from the saga/HTTP/auth stack, and gates whether Task 3's ASB-native implementation is accepted as-is or needs escalation to the Quartz.NET-for-both-environments fallback RESEARCH.md already documents.

Purpose: Make the saga state machine the single, inspectable source of truth for checkout orchestration and compensation, per ADR-0005 (orchestration, not choreography) — without shipping CHK-05 on an unverified assumption about emulator fidelity.
Output: Extended `OrderStateMachine`, `Order` aggregate, `OrderReadModel`/`OrderReadModelProjector`, new `CheckoutOptions`/`CheckoutTimeoutExpired`, EF migration, extended unit test suite, ADR-0009, a standalone ASB-emulator scheduling spike with a recorded PASS/FAIL outcome, and RESEARCH.md's Open Question 1 marked resolved.
</objective>
