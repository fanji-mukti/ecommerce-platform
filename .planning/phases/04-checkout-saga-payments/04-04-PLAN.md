    - `RefundPayment` for a `CheckoutId` with an existing `ProcessedPayment` row → row's `Outcome` becomes `"Refunded"`, `PaymentRefunded` published once; a second identical `RefundPayment` delivery is a no-op (no duplicate `PaymentRefunded`).

  <action>
    `AuthorisePaymentConsumer(PaymentsDbContext db, IPublishEndpoint publish) : IConsumer&lt;AuthorisePayment&gt;`: in `Consume`, first `var existing = await db.ProcessedPayments.FindAsync([msg.CheckoutId], context.CancellationToken);` — if not null, republish the STORED outcome (`existing.Outcome == "Authorised" ? new PaymentAuthorised(...) : new PaymentFailed(..., existing.FailureReason!, ...)`) using stored `Amount`/`FailureReason`, then return (no re-insert, no re-decision — PAY-03). If null, decide: `var cents = decimal.Round((msg.Amount % 1m) * 100m); var endsIn99 = cents == 99m; var shouldFail = msg.SimulatePaymentFailure || endsIn99;` (exact PAY-02 rule). If `shouldFail`, insert `new ProcessedPayment { CheckoutId = msg.CheckoutId, Outcome = "Failed", Amount = msg.Amount, FailureReason = "Payment declined", ProcessedAt = now }`, publish `new PaymentFailed(Guid.NewGuid(), msg.CheckoutId, msg.MessageId, now, msg.CheckoutId, msg.Amount, "Payment declined", now)`. Else insert `Outcome = "Authorised"`, publish `new PaymentAuthorised(Guid.NewGuid(), msg.CheckoutId, msg.MessageId, now, msg.CheckoutId, msg.Amount, now)`. Publish BEFORE `db.SaveChangesAsync(context.CancellationToken)` so the transactional outbox commits message + row atomically (mirrors `OrdersEndpoints.cs`'s publish-then-SaveChanges ordering).
