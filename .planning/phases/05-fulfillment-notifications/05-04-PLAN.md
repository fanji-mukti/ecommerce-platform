<objective>
Build Fulfillment.API out from a bare health-check stub into a working stateless MassTransit consumer: it consumes `OrderStatusChanged`, filters to the `Paid` transition, and schedules `OrderShipped` to publish after a configurable delay (D-01) — no saga, no business persistence, no deterministic failure path (D-02). This is the ONLY genuinely new backend subsystem this phase adds; everything else is contract/wiring changes to existing services.

Purpose: Deliver FUL-01/FUL-02 — the signal that starts and completes the "shipping" simulation the Orders saga (05-03) needs to reach `Fulfilled`.
Output: `FulfillmentDbContext` (outbox/inbox only), `FulfillmentOptions`, `OrderPaidConsumer`, a fully wired `Program.cs` (dual-branch scheduler mirroring Orders.API), an initial EF Core migration, and the AppHost fix for both Fulfillment's and Notifications' missing `postgres` reference.
</objective>
