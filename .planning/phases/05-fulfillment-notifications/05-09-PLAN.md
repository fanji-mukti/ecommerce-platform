<objective>
Close 05-VERIFICATION.md's CR-01 blocker gap: Fulfillment's `OrderPaidConsumer` schedules a delayed `OrderShipped` publish the moment an order becomes `Paid`, with no cancellation path. If the order is subsequently cancelled (via the existing `POST /checkout/{id}/simulate-fulfillment-failure` demo endpoint, reachable while the order is `Paid`), `OrderStateMachine` correctly absorbs the late `OrderShipped` (`During(Cancelled, ...): Ignore(OrderShippedEvent)`), but `OrderShippedNotificationConsumer` has no equivalent guard and unconditionally writes "Your order has shipped." into the customer's inbox for an order that was actually cancelled and refunded.

This plan implements the notification-layer-only fix VERIFICATION.md itself identifies as lowest-risk: give Notifications its own event-driven, locally-maintained record of each order's latest known status (populated by consuming the `OrderStatusChanged` topic it already subscribes to — no new cross-service command/event path, no synchronous lookup, per D-03/PROJECT.md's no-direct-coupling premise), and have `OrderShippedNotificationConsumer` consult that record before writing a "shipped" notification.

Purpose: Make the phase goal's promise — "the user sees the entire lifecycle reflected in an in-app notification inbox" — actually true for the reachable cancel-during-processing-window path, without adding any synchronous service-to-service call or new saga-side compensation plumbing.
Output: `OrderStatusSnapshot` entity + `OrderStatusSnapshotConsumer`, a guarded `OrderShippedNotificationConsumer`, an EF Core migration, and regression tests proving both the suppression case and the unaffected happy-path case.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| ASB topic (Orders → Notifications) | `OrderStatusChanged` is published by the first-party, same-trust-domain Orders service; Notifications now has a second consumer (`OrderStatusSnapshotConsumer`) subscribing to the same topic, unfiltered by status. |
| Notifications DB write path | The new `OrderStatusSnapshots` table is written only by `OrderStatusSnapshotConsumer`, and read only by `OrderShippedNotificationConsumer`'s suppression check — no HTTP-facing endpoint reads or writes it. |
