# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** Per `05-CONTEXT.md` D-05/D-06/D-07/D-08, this phase's UI surface is small and entirely additive to existing pages: (1) a new minimal `/notifications` inbox page, (2) a nav bar link to it, (3) a client-side "Shipping..." indicator on the existing `/orders/:id` page while `status === "Paid"`, and (4) extending `/orders/:id`'s (currently non-existent — see Pitfall 1 in `05-RESEARCH.md`) live-status behavior with polling so the shipping indicator clears automatically once `Fulfilled` is reached. FUL-01/FUL-02 (Fulfillment service) are backend-only and introduce no UI. Note: `/checkout`'s existing polling `TERMINAL_STATUSES` array already includes `'Fulfilled'` (verified in `checkout-page.component.ts`) — no change needed there.

Not re-asked — carried forward as-is, per this project's established precedent of reusing rather than re-deriving the design system per phase.

**Existing precedent this phase must follow (do not re-invent):**
- Spacing tokens are CSS custom properties in `src/styles.scss` (`--space-xs` … `--space-3xl`) — reuse verbatim.
- Empty-state and error-state markup/copy shape (heading + body + action button, `text-align: center; padding: 48px 0;`) is established in `cart-page.component.html` / `catalog-list.component.html` / `checkout-page.component.html` — `/notifications`' empty and error states must reuse this exact shape.
- `mat-progress-bar mode="indeterminate"` is the established list-loading indicator (`checkout-page.component.html`), and `mat-spinner diameter="18"` is the established inline in-progress indicator (`checkout-page.component.html`'s Place Order button while `isPlacingOrder()`) — reuse `mat-spinner diameter="18"` for the new "Shipping..." indicator rather than introducing a new spinner size.
- `order-detail.component.ts` currently performs exactly one `ordersService.getOrder(id).subscribe(...)` in `ngOnInit` with **no polling** (`05-RESEARCH.md` Pitfall 1) — this phase adds a net-new `interval(1500).pipe(switchMap(...), takeWhile(...), takeUntilDestroyed(...))` block, structurally copied from `checkout-page.component.ts`'s `startPolling`, not an "extension" of pre-existing polling code.
- `app.html`'s toolbar conditionally renders authenticated-only links (`Cart` link wrapped in `@if (isAuthenticated().isAuthenticated)`) — the new `Notifications` link (D-06) follows the identical conditional-visibility pattern, placed after `Cart`.
- IDOR-safe pattern: `GET /notifications` is JWT-scoped server-side (per `05-RESEARCH.md`) — the Angular service performs no client-supplied user-id filtering; this is a backend contract, noted here only so the frontend never attempts to pass a `userId` parameter.

## Spacing Scale

Declared values (must be multiples of 4) — **already defined in `src/styles.scss`, reuse verbatim, do not redeclare:**

| Token | Value | Usage |
|-------|-------|-------|
| xs (`--space-xs`) | 4px | Icon-to-text gap inside a notification list item, spinner-to-text gap in the shipping indicator |
| sm (`--space-sm`) | 8px | Compact spacing: list-item internal padding adjustments, chip/spinner row gap |
| md (`--space-md`) | 16px | Default element spacing: list-item vertical rhythm, card padding |
| lg (`--space-lg`) | 24px | Section padding: heading-to-list gap on `/notifications`, matches `order-detail.component.scss`'s `h1 { margin-bottom: var(--space-lg) }` |
| xl (`--space-xl`) | 32px | Page padding: `.notifications-page { padding: var(--space-xl) }`, matches `.order-detail-page` |
| 2xl (`--space-2xl`) | 48px | Empty/error state vertical padding (`padding: var(--space-2xl) 0`, matches existing pattern exactly) |
| 3xl (`--space-3xl`) | 64px | Not used this phase |

Exceptions:
- Mobile breakpoint at `max-width: 600px` reduces page padding to `--space-md` (16px), matching `.order-detail-page`'s existing `@media` block — apply identically to `/notifications`.
- No new icon-only interactive controls are introduced this phase (the notification list items are full-row `routerLink` targets, not icon buttons), so the 44×44px touch-target exception from Phase 3/4 does not apply here — flagged explicitly so the checker does not expect it.

## Typography

Reuses Phase 4's declared roles verbatim — **do not introduce new sizes/weights**:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 (regular) | 1.5 |
| Label | 14px | 400 (regular) | 1.5 |
| Heading | 20px | 500 (medium) | 1.2 |
| Display | 28px | 500 (medium) | 1.2 |

Exactly 4 sizes, exactly 2 weights (400/500 — matches project-wide convention; 700 remains loaded/unused).

Usage mapping for this phase's UI:
- **Heading (20px/500):** `/notifications` page `<h1>` follows the existing unstyled-`<h1>`-with-`margin-bottom`-only convention (verified: `cart-page`, `catalog-list`, `order-detail` all style only `margin-bottom`, not `font-size`, on `h1` — this phase does not deviate) — no explicit font-size override needed; note this only so the checker does not flag a "missing Display size on page title" as an error.
- **Body (16px/400):** notification message text ("Your order has been paid.", "Your order has shipped.", "Payment failed for your order."), the shipping-indicator text ("Preparing your shipment…").
- **Label (14px/400):** notification timestamp text, empty/error-state body copy.
- **Display (28px/500):** not used this phase (no grand-total-equivalent element on `/notifications` or in the shipping indicator).

## Color

Reuses the existing Material Indigo/Pink prebuilt theme tokens already loaded project-wide — **no new hex values introduced this phase.**

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#fafafa` | Page background (`body { background-color: #fafafa }`) |
| Secondary (30%) | `#ffffff` (mat-list/card surface) / `#3f51b5` (mat-toolbar) | `/notifications` list surface, top nav bar |
| Accent (10%) | `#3f51b5` (Material `primary`/indigo) | **Reserved for exactly:** the active-state indicator on the "Notifications" nav link (`routerLinkActive="active-link"`), the "Shipping..." `mat-spinner` on `/orders/:id`, the "Retry" button on `/notifications`' error state |
| Destructive/semantic | `#d32f2f` (matches existing `.error-state h2` / `.failure-reason` color) | **Reserved for exactly:** the `error` icon on a `PaymentFailed` notification list item — no other new use this phase |

Accent reserved for: nav link active indicator, shipping spinner, notifications-page Retry button. **Not** used for the `payment`/`local_shipping` notification icons (kept default/neutral text color — see note below) or for the list items themselves, which are plain clickable rows, not buttons.

Note on notification icon color discipline: only the `PaymentFailed` icon (`error`) is colored (destructive red) to visually flag a negative outcome, consistent with `order-detail.component.html`'s existing `Cancelled`/`Failed` status-chip red treatment. The `payment` (paid) and `local_shipping` (shipped) icons stay unstyled/inherit color — they are positive/neutral informational events, and coloring them accent would violate the "accent reserved for a short, specific list" discipline established in Phase 3/4's UI-SPECs.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | **None new this phase.** There is no single highest-priority conversion action on `/notifications` — each inbox entry is itself an implicit navigation target (`routerLink="/orders/{{ n.orderId }}"` on the full `mat-list-item` row), consistent with D-05's "linking to `/orders/:id`" and mirroring Phase 3's precedent of not forcing an accent CTA where none is warranted. |
| Notification — order paid (D-04, locked) | **"Your order has been paid."** |
| Notification — order shipped (D-04, locked) | **"Your order has shipped."** |
| Notification — payment failed (D-04, locked) | **"Payment failed for your order."** |
| Notifications page title | **"Notifications"** |
| Nav link label (D-06, locked) | **"Notifications"** (plain `mat-button`, no unread-count badge — explicitly deferred to NOT-V2-01 per D-06) |
| Empty state heading | **"No notifications yet"** |
| Empty state body | **"Updates about your orders will show up here."** (no action button — unlike cart/catalog empty states, there is no single "go do this" next step; browsing/checkout are already globally reachable via the nav bar) |
| Error state heading | **"Failed to load notifications"** |
| Error state body | **"Something went wrong while loading your notifications. Please refresh the page or try again."** + `mat-raised-button color="primary"` **"Retry"** — verbatim reuse of the `cart-page`/`checkout-page` error-state wording template (`{{ noun }}` swapped to "notifications") |
| Shipping indicator (D-07, working copy from CONTEXT.md, finalized here) | **"Preparing your shipment…"** — shown inline below the status chip on `/orders/:id`, only while `status === 'Paid'`; disappears automatically once polling (D-08) observes `Fulfilled` |

## UI Considerations

Applicable state considerations resolved for the notifications list (list-collection) and the shipping indicator (status-derived element):

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | notifications list (list-collection) | ✅ covered | "No notifications yet" / "Updates about your orders will show up here." — see Copywriting Contract |
| loading | notifications list (list-collection) | ✅ covered | `mat-progress-bar mode="indeterminate"` while `GET /notifications` is in flight — reuses `checkout-page` pattern |
| error | notifications list (list-collection) | ✅ covered | "Failed to load notifications" + Retry button — see Copywriting Contract, reusing `.error-state` SCSS shape |
| populated | notifications list (list-collection) | ✅ covered | Typical volume (a handful per demo user, per `05-RESEARCH.md` Open Question 2) renders as stacked `mat-list-item` rows, each with icon + message + order link |
| zero-one-many | notifications list (list-collection) | ✅ covered | Zero → empty state; one/many → same stacked-row layout, no pluralization copy needed (no "N notifications" count header this phase) |
| overflow | notifications list (list-collection) | ✅ covered | No pagination this phase (`05-RESEARCH.md` Open Question 2 recommendation: skip for v1) — relies on native page scroll, acceptable at demo data volumes; flagged as a natural NOT-V2 addition if needed |
| in-progress / intermediate | order status on `/orders/:id` (status-derived, not a collection) | ✅ covered | D-07's "Shipping..." indicator is a pure client-side inference from `status === 'Paid'` — no backend state, no loading/error variant needed beyond the page's existing `isLoading`/`notFound` states |
| stale-on-navigate | `/orders/:id` reached directly (bookmark, refresh, order-detail link) while order is still `Paid` | ✅ covered | D-08's new polling block ensures the page does not show a static "Paid" snapshot forever — it polls every 1.5s until `Fulfilled`/`Cancelled`/`Failed`, matching `/checkout`'s existing terminal-status set |
