<objective>
## Phase Goal

**As a** logged-in user, **I want to** build a cart with price-snapshotted line items and view my order history through an event-driven read model, **so that** I can review what I'm about to buy and track past orders before the real checkout flow lands in Phase 4.

*(ROADMAP.md's Phase 3 `**Goal:**` line is outcome-prose, not the strict "As a/I want to/so that" template emitted by `/gsd mvp-phase`. This story is derived verbatim from that Goal line's actor/capability nouns — no new scope invented. Flagged to the user in the planning summary.)*

Build the Cart service end-to-end: a logged-in user can add, remove, and update quantities of items in a per-user Redis cart, with price/name captured server-side from Catalog at add-time (never trusting the client), and view a cart summary with line totals and a grand total. This is the first Cart implementation in the codebase (previously a bare stub) and the first service requiring JWT-bearer authentication besides Identity itself — it also establishes the AppHost/Gateway wiring both other Phase 3 plans depend on.

Purpose: CART-01/02/03 (add/remove/update, price snapshot, cart summary) plus the cross-cutting infrastructure (Aspire service references, YARP routes) that Plan 03-03 (Orders API) and Plan 03-04 (Angular /cart) build on.
Output: Working `GET/POST/PATCH/DELETE` Cart endpoints behind JWT auth, reachable via the gateway at `/api/cart/**`, with a Redis-backed store and a synchronous Catalog price-snapshot client.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Browser (Angular) -> Gateway -> Cart.API | Untrusted client input crosses at the gateway; Cart.API must independently authenticate/authorize |
| Cart.API -> Catalog.API | Internal service-to-service HTTP call (D-04), not routed through YARP, semi-trusted network |
| Cart.API -> Redis | Internal data store, not internet-exposed |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Spoofing | CartEndpoints (all 5 routes) | high | mitigate | JwtBearer auth validated against Identity's authority; `.RequireAuthorization()` on every endpoint; verified by a 401-without-token test |
| T-03-02 | Tampering | CartEndpoints POST/PATCH request binding | high | mitigate | AddCartItemRequest/UpdateCartItemQuantityRequest never carry price/name fields; UnitPrice/ProductName always sourced from ICatalogPriceClient server-side (P1 prohibition) |
| T-03-03 | Information Disclosure | Cart user-scoping | medium | mitigate | Cart key derived exclusively from the JWT sub claim, no userId route/query parameter exists — structurally prevents cross-user cart access (no route to exploit) |
| T-03-04 | Denial of Service | Redis cart size (unbounded item/quantity growth) | low | accept | Single-user portfolio demo scope, no production traffic; no cap implemented |
| T-03-05 | Tampering | Cart.API -> Catalog.API internal HTTP (no mTLS/signing) | low | accept | Aspire-orchestrated internal network only, not internet-exposed; consistent with the existing Gateway->service trust model established in Phase 2 |
| T-03-SC | Tampering (supply chain) | New NuGet packages (Aspire.StackExchange.Redis, Microsoft.AspNetCore.Authentication.JwtBearer) | low | accept | Official Microsoft-published packages (not npm/pip/cargo — package legitimacy gate does not apply to NuGet); verify exact version against nuget.org before pinning |
