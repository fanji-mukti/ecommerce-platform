## Phase Goal

**As a** logged-in user, **I want to** build a cart with price-snapshotted line items and view my order history through an event-driven read model, **so that** I can review what I'm about to buy and track past orders before the real checkout flow lands in Phase 4.

*(Derived from ROADMAP.md's Phase 3 outcome-prose Goal line — see Plan 03-01's objective for the full note.)*

Build the `/cart` page: an Angular Material-based cart view (loading/empty/error/populated states per 03-UI-SPEC.md), wired to Plan 03-01's Cart API through the gateway, with debounced quantity updates and a functioning "Add to Cart" entry point from the product detail page (previously a disabled placeholder). After this plan, a real user can click "Add to Cart" on any product, land on `/cart`, adjust quantities, remove items, and see a correctly-totaled summary — the full FE-02 vertical slice.

Purpose: FE-02 (manage cart at /cart), wiring the only client-facing entry point CART-01 needs (the product-detail "Add to Cart" button).

</objective>

PATCH /api/cart/items/{productId} { quantity } -> 200 with updated cart (absolute set, 400 if quantity < 1)
DELETE /api/cart/items/{productId} -> 200 with updated cart (404 if not present)
DELETE /api/cart -> 204

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-13 | Information Disclosure (XSS) | Cart line-item product name rendering | medium | mitigate | Angular's default `{{ }}` interpolation auto-escapes; no `[innerHTML]` or `bypassSecurityTrustHtml` used for product name/description |
| T-03-14 | Tampering | Client-side cart totals | low | accept | Grand total is always re-derived from the server's GET /cart response on load and after every mutation — never a client-only computed value trusted for display integrity beyond cosmetic optimistic updates |
| T-03-15 | Spoofing | Unauthenticated access to /cart route | low | mitigate | No client-side route guard exists yet (consistent with the rest of the app's routes), but the backend enforces 401; CartPageComponent explicitly redirects to /login on a 401 response rather than showing a generic error |

</threat_model>
