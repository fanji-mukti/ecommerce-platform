    0001-use-madr-format.md
    - Title: "Use MADR 4.0 for Architectural Decision Records"
    - Problem: Need a lightweight, reviewable, file-based ADR format that integrates with git
    - Options: MADR 4.0, plain markdown (freeform), RFC-style, Log4Brains
    - Chosen: MADR 4.0 — structured frontmatter enables tooling; simpler than RFC; more standard than freeform
    - More Information: link to adr.github.io/madr/, note planned ADR count (~26 by Phase 6)

    0002-azure-service-bus.md
    - Title: "Use Azure Service Bus as the Async Messaging Backbone"
    - Problem: Need an async message broker for event-driven coordination across 8 microservices with Azure deployment target
    - Options: Azure Service Bus, RabbitMQ, Apache Kafka, in-process events (MediatR)
    - Chosen: ASB — native Azure, topics/subscriptions fit bounded context design, managed identity auth, KEDA integration for ACA scaling
    - Consequences — Bad: Standard tier required (Basic has no topics), no emulator data persistence across restarts
    - More Information: link to ADR-0007 (topic design), ADR-0006 (MassTransit)

    0003-database-per-service.md
    - Title: "Enforce Database-per-Service Isolation"
    - Problem: Multiple services need persistence; shared DB creates coupling and violates service autonomy
    - Options: Shared database (single schema), shared database (per-service schema), database per service
    - Chosen: Database per service — each service owns its schema and connection string
    - Note in Consequences: Phase 1 provisions one shared Postgres container for simplicity; enforcement is at connection-string level (each service gets its own database in the shared container). Separate containers enforced from Phase 2+.
    - More Information: link to ADR-0005 (saga pattern), note that cross-service queries are prohibited

    0004-yarp-api-gateway.md
    - Title: "Use YARP as the API Gateway"
    - Problem: Angular SPA and external clients need a single entry point to route to 8 independently-deployed services
    - Options: YARP (Yet Another Reverse Proxy), Ocelot, Azure API Management, no gateway (direct service calls)
    - Chosen: YARP — actively maintained by Microsoft, .NET native, reverse proxy config via appsettings, Ocelot is in maintenance mode
    - More Information: Note YARP is implemented in Phase 2; this ADR locks the choice now

    Write 4 ADR files using the same MADR 4.0 frontmatter and 7-section structure as Task 1.

    Content guidance per file:

    0005-saga-orchestration.md
    - Title: "Use Saga Orchestration over Choreography for Checkout"
    - Problem: Checkout spans 5 services (Orders, Payments, Fulfillment, Notifications, Catalog). Need a coordination pattern with explicit state and compensation paths.
    - Options: Orchestration (central process manager / state machine), Choreography (event chain, no central coordinator)
    - Chosen: Orchestration — explicit state machine makes compensation paths visible and testable; single place to observe saga progress; MassTransit state machine is purpose-built for this
    - Consequences — Bad: Single saga state machine is a coupling point; if it fails, coordination stops
    - More Information: link to ADR-0006 (MassTransit as the implementation), Phase 4 implements the saga

    0006-masstransit-outbox-inbox.md
    - Title: "Pin MassTransit to 8.3.6 (Apache-2.0) with Transactional Outbox and Idempotent Inbox"
    - Problem: Need a messaging abstraction over ASB with saga support, transactional outbox, and idempotent inbox. MassTransit v9 exists but has a commercial license change.
    - Options: MassTransit 8.3.6 (Apache-2.0), MassTransit 9.x (Massient commercial), NServiceBus (Particular Platform commercial), Raw Azure.Messaging.ServiceBus SDK
    - Chosen: MassTransit 8.3.6 — last Apache-2.0 release, receives security patches through end of 2026, mature saga state machine support, EF Core outbox integration
    - MUST document these 3 points in Consequences or More Information:
      1. v9 license: MassTransit 9.x requires a Massient commercial license; unacceptable for an OSS portfolio project
      2. EmulatorHost() absent: The EmulatorHost() API does not exist in v8.3.6 (added in v9). Phase 2 must test AMQP connectivity via Aspire-injected connection string and may need ServiceBusClientOptions workaround
      3. v8 EOL: MassTransit v8 receives security patches through end of 2026; a license re-evaluation is needed in Q4 2026 if v8 EOL is confirmed
    - Rejected: NServiceBus (commercial Particular Platform license), raw SDK (no saga, no outbox, no test harness)
    - More Information: link to massient.com for license details, link to ADR-0005 (saga pattern depends on this choice)

    0007-asb-topic-per-context.md
    - Title: "Use One ASB Topic per Producing Bounded Context"
    - Problem: Each service publishes multiple message types. Need a topic naming strategy that balances entity count limits and bounded context alignment.
    - Options: One topic per message type (N topics per service), one topic per producing bounded context (1 topic per service), one shared topic for all services
    - Chosen: One topic per producing bounded context — aligns with bounded context principle, minimizes ASB entity count (8 topics max vs potentially 40+ with per-message topics), simpler subscription topology
    - Implementation note: MassTransit default behavior creates topics per message type. Override using [EntityName("catalog-events")] attribute on records or via cfg.Message<T>(x => x.SetEntityName(...)) in bus config. This override is implemented in Phase 2 (first MassTransit config).
    - Emulator constraint: ASB emulator supports max 50 entities per namespace — topic-per-context stays well within this limit
    - More Information: link to ADR-0006, note Phase 2 implements the [EntityName] override

    0008-mono-repo-multi-solution.md
    - Title: "Mono-Repo with Independent Per-Service Solution Files"
    - Problem: 8 services share a Contracts library and infrastructure. Need a repo structure that enables independent service development in Visual Studio while maintaining shared contracts.
    - Options: Mono-repo with one solution (all projects in one .sln), poly-repo (8 separate git repos), mono-repo with per-service solutions
    - Chosen: Mono-repo with per-service solutions — each service .sln is independently openable in Visual Studio; Contracts shared via ProjectReference (not NuGet, so changes are immediately visible without publishing); all services visible in one git history for cross-cutting changes
    - Consequences — Bad: dotnet build at repo root does not work without a root-level solution; CI must specify each .sln path explicitly
    - More Information: link to ADR-0001 (MADR format used here), note CI matrix in .github/workflows/ci.yml handles the 10-solution build
